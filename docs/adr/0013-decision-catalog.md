# ADR-0013 — Каталог решений как единый источник и одинаковая валидация в Python и web

- Статус: Accepted
- Дата: 2026-10-28
- Этап: 05

## Контекст

Decision Builder и будущий `POST /api/v1/scenarios/validate` должны применять одни и те же диапазоны, единицы и межполевые правила. Если диапазоны лежат в Pydantic-валидаторах и отдельно в форме, они разойдутся: форма пропустит то, что отвергнет API, или наоборот. JSON Schema межполевые правила не выражает (ADR-0008, п. 6).

## Решение

1. **Каталог** `multiverse_contracts.interventions.CATALOG` описывает для каждого из шести типов:
   - единицы величины и чем каждая отличается;
   - жёсткие и planning-диапазоны;
   - defaults с типом источника: accounting rule, statutory rate, design default, placeholder;
   - лаг и разгон;
   - доли финансирования;
   - механизм по отчётам;
   - «что это не значит»;
   - уровень доказательств.

   Каталог сам проверяется contracts-моделями: planning-диапазон лежит внутри разрешённого, default — внутри диапазона, доли в сумме дают ровно 1.
2. **Модели решений** — по одной на тип, discriminated union по `type`, поля совпадают с ключами каталога (это проверяет тест). Валидаторы читают диапазоны из каталога.
3. `python -m multiverse_contracts.catalog` пишет `packages/contracts/catalog/interventions.json`. Web импортирует его через `@multiverse/contracts/interventions`; файл проверяется на дрейф в `contracts:check`. Это и есть будущий ответ `GET /api/v1/interventions/types`.
4. **Коды правил.** Нарушение правила имеет стабильный код в квадратных скобках (`[shares_sum]`) и путь поля (`decision.financing`). Web-валидатор (`apps/web/src/decisions/rules.ts`, `parse.ts`) выдаёт те же коды и пути. Структурные ошибки названы как типы ошибок Pydantic: `missing`, `extra_forbidden`, `string_type`, `union_tag_invalid`.
5. **Общие fixtures** `packages/contracts/fixtures/valid.json` и `invalid.json` (модель `ScenarioDraft`) проходят и pytest, и vitest. Для невалидных случаев оба языка должны выдать одинаковый код.
6. **Eligibility.** Правила, которым нужны данные компании на дату знаний (unsupported, мало истории, нет базы для относительной единицы, выход с рынка, OOD, крупная сделка), пока живут в web (`eligibility.ts`) поверх point-in-time dossier. Их серверная версия появится вместе с `POST /scenarios/validate`.

## Как проверяется

- `uv run pytest packages/contracts`: поля моделей равны ключам каталога; defaults образуют валидный сценарий; доли сравниваются как decimal (property-тест, 300 случаев); каталог не устарел.
- `npm run test --workspace @multiverse/web`: обе выборки fixtures дают те же коды, что и в Python.
- `npm run contracts:check`.

## Последствия

Новый параметр добавляется так:

1. ключ в каталоге;
2. поле в модели решения;
3. `npm run contracts:gen`.

Если забыть второй шаг, это поймает тест «поля равны каталогу», а форма подхватит параметр сама. Planning-диапазоны и пороги относительного размера — design defaults; на Stage 14 их заменят диапазонами, измеренными на данных.

## Отвергнутые альтернативы

- **Общая модель решения с `parameters: dict`.** Каталог остался бы онтологией, но схема и TypeScript потеряли бы точные поля каждого типа, а финансовому движку (Stage 21) нужны именно они.
- **Zod-схемы в web, сгенерированные из JSON Schema.** Межполевых правил в схеме нет, так что их всё равно пришлось бы писать руками.
- **Валидация только на сервере.** API появится не раньше Stage 10–12, а форма нужна сейчас. Это ещё и противоречило бы цели «ошибка у конкретного поля сразу» (FC-05).
