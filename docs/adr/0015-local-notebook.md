# ADR-0015 — Notebook на устройстве: неизменяемые revisions, неизменяемые отчёты, импорт без перезаписи

- Статус: Accepted
- Дата: 2026-10-29
- Этап: 07

## Контекст

В V1 нет аккаунтов и сервера (D-07, SP-02), но сценарии нужно сохранять, видеть их историю, экспортировать отчёты и переносить между браузерами (FR-LB-01…03, FR-RP-01…04). Браузерное хранилище может отсутствовать (private mode), переполниться или содержать данные, которые эта версия не может прочитать (FC-10).

## Решение

1. **Contract** (contracts 0.5.0):
   - `ScenarioRecord`: name, tags, notes и непустой список `ScenarioRevision`;
   - `ReportSnapshot`: отчёт Markdown, SHA-256 содержимого, manifest;
   - `NotebookExport`: файл со `schema_version`.

   Правила contract:
   - revisions нумеруются подряд;
   - родитель раньше потомка;
   - все revisions одного сценария — для одной компании;
   - статус результата согласован с ID результата;
   - хэш совпадает с содержимым;
   - отчёт ссылается на существующую revision, помеченную exported;
   - demo-файл заканчивается на `_DEMO.md`;
   - лишние поля отклоняются.
2. **Revisions только добавляются.** Правка в Decision Builder — новая revision с `parent_revision`. Дубль — новый сценарий с `derived_from`. Name, tags и notes описывают сценарий и revision не создают.
3. **Отчёт — неизменяемый snapshot.** Содержимое и manifest зависят только от revision, так что повторный экспорт даёт тот же текст и manifest (US-12), но это новый snapshot с новым ID. Старый не заменяется (FR-RP-03). После экспорта revision помечена exported. Сценарий с отчётами удалить нельзя.
4. **Хранилище** — один ключ `multiverse.notebook` в localStorage в формате `NotebookExport`. Один парсер и один путь миграции служат и хранилищу, и импорту. Ошибки записи (quota, unavailable) видны пользователю, изменение остаётся в памяти вкладки, предлагается экспорт. Нечитаемые данные не перезаписываются: их можно скачать или сбросить после подтверждения.
5. **Импорт** проверяет файл целиком и сливает его только если он валиден:
   - файл новой версии отклоняется;
   - JSON решения из Stage 05 мигрирует в сценарий с одной revision;
   - слияние никогда не перезаписывает: тот же ID с другим содержимым становится копией, а отчёты копий не переносятся, потому что их manifest называет исходный ID.
6. **Сравнение revisions.** Разные cutoff, горизонт или валюта блокируют сравнение: метода выравнивания пока нет.

## Как проверяется

- pytest `test_notebook.py`: общий файл валиден и проходит round trip; 18 видов сломанного файла отклоняются.
- vitest `notebook.test.ts`: неизменяемость, отчёты, quota / private / повреждённые данные, импорт и миграция, слияние, сравнение.
- Playwright `notebook.spec.ts` на трёх ширинах: сохранение, обновление страницы, восстановление формы, экспорт, отказы хранилища, удаление всех данных.

## Последствия

Серверное хранилище (V4, Stage 24) примет те же `ScenarioRecord` и `ReportSnapshot` через `POST /api/v1/scenarios`, а импорт из файла станет способом переноса локальных данных на сервер. При переходе схемы на версию 2 миграция v1 → v2 добавляется в тот же парсер.

## Отвергнутые альтернативы

- **IndexedDB.** Больше места, но асинхронный API и сложнее тесты. Объём V1 — десятки сценариев по нескольку KB, localStorage хватает. При росте можно перейти без смены формата.
- **Правка revision на месте до экспорта.** Проще для пользователя, но история теряется, а сравнение «что изменилось» становится невозможным.
- **Автоматическая перезапись при импорте.** Риск тихо потерять более новую локальную версию.
