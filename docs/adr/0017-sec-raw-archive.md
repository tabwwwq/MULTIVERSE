# ADR-0017 — Сырой архив SEC: неизменяемые файлы по SHA-256, append-only индекс, загрузки только явной командой

- Статус: Accepted
- Дата: 2026-10-29
- Этап: 10

## Контекст

Stage 10 впервые загружает реальные данные SEC. Их будут читать нормализация (Stage 11) и point-in-time хранилище (Stage 12). Поэтому нужно доказать, что именно было получено, когда и по какому адресу, и что файл с тех пор не менялся. SEC не публикует checksums (ADR-0016). API data.sec.gov не отдаёт `Last-Modified` и `ETag`, а bulk-файлы на www.sec.gov отдают. Соединение может оборваться, SEC может ответить 429 или 403. Ответ может оказаться короче заявленного, ZIP может быть повреждён. Владелец разрешил только sample (решение D-09); bulk ждёт решения D-10.

## Решение

1. **Три замка перед каждой загрузкой** (`gate.py`):
   - `MULTIVERSE_ALLOW_NETWORK_DOWNLOADS=true` задаётся на одну команду, а `.env` хранит `false`;
   - `MULTIVERSE_SEC_USER_AGENT` содержит имя и email;
   - решение в каталоге `approved`. Для bulk нужна область `bulk`: contracts 0.7.0 добавили `DownloadDecision.scope`. Ничего не запускается по расписанию (`automatic_downloads: disabled`).
2. **Клиент** (`client.py`):
   - только официальные хосты источника по HTTPS, в том числе после redirect;
   - один process-wide throttle на выбранной скорости (2 запроса в секунду);
   - повтор при 429 и 5xx: backoff 10 / 20 / 40 с плюс jitter или `Retry-After`, если он длиннее. `Retry-After` больше 10 минут означает «не сейчас», и клиент сдаётся;
   - повтор при оборванном соединении и при теле короче `Content-Length`;
   - 403 останавливает весь запуск;
   - тело пишется потоком во временный `.part` с лимитом по бюджету диска.
3. **Файл попадает в архив только после проверки** (`validate.py`):
   - JSON разбирается целиком, CIK совпадает с запрошенным;
   - у таблицы filings колонки одинаковой длины, у каждого факта есть `accn`, `filed`, `end`, `val`, `form`;
   - каждый член ZIP проходит CRC, в FSDS есть `sub/num/tag/pre.txt`.
4. **Неизменяемое хранение** (`archive.py`):
   - путь `var/raw/sec/<dataset>/<key>/<sha256>.<json|zip>`; файл переносится атомарно и получает атрибут read-only;
   - тело хранится как опубликовано: HTTP gzip снят, ZIP остаётся ZIP. Сжатие на проводе записывается в `content_encoding`;
   - одинаковые байты не хранятся дважды; изменившийся файл становится новым объектом рядом со старым.
5. **Метаданные:**
   - `index.jsonl` — одна строка `RawObject` на файл. В строке: URL, SHA-256, размер, `Content-Length`, `Last-Modified`, `ETag`, `downloaded_at` (UTC), run, число filings, последний accession и дата подачи, лицензия и дата проверки terms, версия каталога;
   - `runs/<run>.json` — `RunManifest` каждого запуска со всеми запросами, включая не сохранившие ничего: `fresh_in_archive`, `not_modified`, `unchanged`, `stale_response`, `failed`;
   - вместо User-Agent записывается имя настройки, потому что в нём email.
6. **Свежесть и устаревший кэш:**
   - файл, который источник подтвердил не позже `--max-age-hours` назад (12 ч), не запрашивается снова;
   - более старый перепроверяется conditional-запросом, если есть validators. 304 ничего не сохраняет;
   - ответ с `Last-Modified` старше архивного считается устаревшей копией и не сохраняется.
7. **Восстановление:** `.part` прошлого прерванного запуска удаляется при старте. Файл, который успел попасть на место без строки индекса, принимается после сверки SHA-256. `verify` перехеширует архив и находит изменённые, пропавшие, доступные для записи и неизвестные файлы.
8. **Bulk** (`companyfacts.zip`, `submissions.zip`, квартальный FSDS) — только командой `bulk` с `--max-mb` и после решения `bulk` в каталоге. Сначала идёт HEAD: файл, который больше лимита или бюджета, не загружается.

## Как проверяется

`pipelines/tests`: 68 тестов на синтетических fixtures через `httpx.MockTransport`. Настоящий HTTP-transport в тестах заблокирован. Проверяются 429 и `Retry-After`, 5xx и backoff, 403, обрыв соединения, неполное тело, чужой хост и redirect, превышение бюджета, повреждённый и обрезанный ZIP, неполный JSON, устаревший кэш (свежий, 304, те же байты, старый `Last-Modified`), восстановление после сбоя, `verify` и все три замка.

## Последствия

- Stage 11 читает только файлы из индекса и знает их происхождение; повторный запуск ничего не дублирует.
- Для JSON API conditional-запросы не работают: SEC не отдаёт validators. Перепроверка загружает файл заново (gzip), и дубль отсекает SHA-256.
- Атрибут read-only защищает от случайной записи, но не от владельца машины; доказательство — `verify`.
- Бюджет диска (`MULTIVERSE_RAW_BUDGET_MB`, по умолчанию 200) останавливает запуск. Для bulk его поднимает владелец вместе с решением D-10.

## Отвергнутые альтернативы

- **Хранить байты с провода (gzip).** Их SHA-256 зависит от того, как сервер сжал ответ, и тогда одинаковое содержимое дало бы разные объекты.
- **Индекс в SQLite или DuckDB.** На этом этапе append-only JSONL проще проверить глазами и восстановить. Таблицы появятся в хранилище Stage 12.
- **Перезапись файла по URL.** Она теряет прошлые версии и делает point-in-time невозможным.
- **Ticker как ключ.** Тикеры меняются и переиспользуются, поэтому ключ — CIK из 10 цифр.
